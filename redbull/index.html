Disclosure Report — Web Security

The Slot That Took Any Number

An unauthenticated write endpoint in a vending-machine management platform let anyone create or overwrite any record in the production database — no login, no token, no ownership check. Just a number.

Read time 7 min Class IDOR / Broken Access Control Note Reported as a duplicate finding

There is a particular kind of vulnerability that doesn't need cleverness — it just needs a number you're allowed to type into a box. That's the entire shape of what I found in the public-facing vending machine management system used across Red Bull's Italian distribution network: an endpoint called /saveVending that would write to the production database for absolutely anyone who asked, and would overwrite anything already sitting at the address you gave it.

No login screen stood in the way. No session cookie was checked. No token was issued, inspected, or required. This vulnerability, which I found and reported, falls into one of the oldest and most consistently underestimated bug classes on the web: the Insecure Direct Object Reference, or IDOR. It is rarely about clever exploitation, only ever about absent verification.

The setup

Picture the system this endpoint belongs to: field agents driving routes, visiting bars, offices, and gyms, checking on vending machines, logging product availability, noting competitor presence, occasionally registering a brand-new machine that's just been installed. Every one of those actions, in the application's design, becomes a POST request to a server somewhere, carrying a record ID and a pile of form fields.

That record ID — vendingid — is the entire hinge the system swings on. Send 0, and the server treats the request as new. Send a real existing ID, and the server treats it as an edit. The question I asked was deceptively simple: what happens if I send a number that isn't mine?

Finding one — a record born from nothing

The first test required no special access at all — just a browser console open on the live application and a single fetch call.

Request — POST /saveVendingunauthenticated
fetch('/saveVending', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({
    vendingid:   '0',
    nome:        'TestShop',
    tipologia:   'BAR',
    grossista:   'TestGrossista',
    latitudine:  '45.08',
    longitudine: '7.69'
  })
}).then(r => r.json()).then(console.log);
Server responded "result": true and assigned a fresh production ID — vendingid 6061. No credentials presented.

That last detail matters more than it first appears. A result of true and a real, sequential ID handed back means the request didn't bounce off a sandbox or a staging mirror — it landed in the live ledger that real field agents read from every day. Required-looking fields like address and city were accepted blank, which tells you something too: validation, where it existed, lived entirely in the browser, decorative rather than enforced.

Finding two — the overwrite

The second test is the one that turns a sloppy form into an actual vulnerability. If a brand-new record could be created by guessing 0, what happens if you address an ID that already belongs to someone else?

Request — POST /saveVendingIDOR confirmed
fetch('/saveVending', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({
    vendingid:   '6061',        // targeting the record just created
    nome:        'OVERWRITTEN',
    tipologia:   'BAR',
    grossista:   'ATTACKER',
    latitudine:  '45.08',
    longitudine: '7.69'
  })
}).then(r => r.json()).then(console.log);
Server echoed back the attacker-supplied values as the new state of record 6061. No ownership, session, or origin check intervened.

The server never asked "whose record is this?" — only "which number did you send?"

That's the whole vulnerability, distilled to one sentence. I stopped immediately at confirmation — no loop, no automation, no enumeration of the roughly six thousand other IDs that the same flaw would plainly reach. But the math of it is unavoidable: any integer between 1 and 6059 sent through the same request would rewrite a real machine's name, operator, location, and coordinates, in seconds, at scale, from a single unauthenticated script.

What's actually exposed

An IDOR on a single endpoint rarely stays a single-endpoint problem. The same absence of session checking that lets /saveVending through almost certainly extends to sibling endpoints built on the same pattern, and the report lays out four distinct ways the damage compounds.

Data integrity

A simple loop across the ID range could rewrite name, location, operator, and coordinates for every vending machine in the system — corrupting routing, reporting, and analytics built on top of that table.

Reporting & KPIs

If the companion endpoint /saveVisita shares the same lack of authentication, anyone could file unlimited fake visit reports under any agent's name, quietly poisoning every dashboard downstream.

Competitive exposure

A location-lookup endpoint returning names, addresses, and visit history for any coordinate means a competitor could map the entire distribution network's coverage and density without ever touching a login form.

Agent privacy

Field agent names, phone numbers, and emails travel through these same unauthenticated POST bodies and land in storage — personal data effectively readable by anyone who can reach the API.

Why this keeps happening

IDOR bugs survive because they hide behind something that looks like it's working. The endpoint returns a clean JSON success. The UI updates. Nothing throws an error. The only thing missing is a question the server should have asked at every single write: not "is this request well-formed," but "does the person sending it have any right to touch this record?" Client-side validation can make a form feel safe while leaving the actual gate wide open, and that gap is exactly where this bug lived.

What should change

  • 01

    Require real authentication on every write. All POST endpoints need a server-issued session token, checked before any processing happens. No token, no write — full stop, returned as a 401.

  • 02

    Authorize the specific record, not just the request. Before touching an existing vendingid, the server has to confirm the authenticated user actually has a claim to that record — region, assignment, ownership, whatever the business rule is — and reject with a 403 otherwise.

  • 03

    Never trust a client-supplied ID. The browser should never be the source of truth for which row gets written. That decision belongs entirely to server-side logic the client can't see or shape.

  • 04

    Re-run validation on the server. Required fields, coordinate ranges, string lengths — every rule the frontend enforces needs an identical, independent check behind it, because frontend rules are suggestions, not gates.

The smallest bugs travel the farthest

What makes this case worth sitting with isn't sophistication — there isn't any. It's that a single unchecked integer, repeated across a few thousand records, was enough to threaten the integrity of an entire operational dataset behind a major commercial route network. My choice to stop at confirmation, rather than push the proof of concept toward a full enumeration, is itself worth noting: the most responsible disclosures often demonstrate exactly enough to prove the door is open, and not one step more.

The fix here isn't exotic either. It's the same sentence security engineers have been writing on whiteboards for two decades: never let the client decide whose record gets touched. The gap between "logged in" and "allowed to do this specific thing" is where almost every IDOR in the wild quietly lives.
